# UI 08: 管理画面フォームUX

## 状態

全体調査・契約整理済み／実装前

## 依存関係

- UI 07

## 目的

偵察、被弾表、DB確認、設定、兵種編集を横断し、入力の意味、実行前の結果予測、保存中・成功・失敗、破壊的操作の対象を迷わず把握できる状態へ整える。API、保存値、パーサー、権限、削除対象は変更しない。

## 現在の構成と責務

| 画面 | URL | 主な実装 | 責務 |
| --- | --- | --- | --- |
| 偵察検索 | `/warlords/scout` | `ScoutTab.tsx` | 複数名照合、TSV/150文字以内の報告文コピー |
| 被弾表 | `/warlords/damage` | `DamageTab.tsx`、`lib/action.ts` | 40分/80分閾値による状態判定、改名前後の統合 |
| DB確認 | `/warlords/db` | `DbTab.tsx`、`lib/warlordStats.ts` | 武将検索・並べ替え、能力値取込、TSVコピー |
| 兵種図鑑 | `/encyclopedia/units` | `UnitTab.tsx`、`UnitEditModal.tsx` | 兵種の検索、一括取込、追加・編集・削除 |
| 環境設定 | `/settings` | `SettingsTab.tsx`、`FactionTab.tsx` | テーマ、過去ログ、国色、データ整理・削除 |
| 配線・権限表示 | `/` | `app/page.tsx`、`lib/tabs.ts` | 公開/管理タブ、詳細画面、管理操作の表示 |
| 保存API | `/api/**` | `lib/api.ts`、Route Handler | JSON契約、認証、DB更新 |

`scout`、`damage`、`db`、`factions`は管理者専用タブで、`history`と`units`は公開タブである。更新APIはUIの表示制御とは独立してサーバー側の`requireAdmin()`で保護され、未認証時は401を返す。

## 維持する外部契約

| 機能 | 維持する契約 |
| --- | --- |
| 武将能力値取込 | `POST /api/warlord-stats`、body `{ stats }` |
| 兵種追加・更新 | `POST /api/unit-types`、bodyは12項目の`UnitType` |
| 兵種一括取込 | `PUT /api/unit-types`、body `{ units }` |
| 兵種削除 | `DELETE /api/unit-types/:name`、名前をURLエンコード |
| 国色保存 | `PUT /api/faction-colors`、差分でなく全色マップ |
| 偵察TSV | `国 / 武将名 / タイプ / 兵種タイプ / 兵種名`の列順 |
| 偵察報告 | `名前［短縮タイプ｜兵種名］`、150文字上限 |
| 被弾判定 | 40分未満、40〜80分、80分以上の閾値と並び順 |
| 兵種複合値 | `金:600`、`武力:40`、`36年`等の文字列表現 |
| 保存後の入力 | 成功時のみクリア、失敗時は入力と例外メッセージを維持 |

## 現状の良い点

- API認可がUIから独立しており、表示漏れが更新権限の突破にならない
- Historyの登録は事前解析、入力保持、部分失敗、二重送信防止が既に整っている
- DB/兵種取込のパーサーは純粋関数で、同名後勝ち、ヘッダー除外、不正行skipがテストされている
- `useModalA11y`はフォーカストラップ、Escape、開始位置への復帰、背景スクロール抑止を備える
- Unitの一括取込は、有効件数をボタン文言へ即時反映している
- 削除確認文は対象名と元に戻せないことを表示している

## 主な問題

| 重大度 | 問題 | 原因・影響 |
| --- | --- | --- |
| ★★★★★ | 未認証でも兵種詳細の「編集」が見える | 保存APIは401だが、利用者には実行可能に見える。表示を変えると既存のユーザー可視挙動も変わる |
| ★★★★★ | 兵種名変更がrenameでなく新規upsertになる | 旧名が残る。編集途中の名前で削除するため、対象の取り違えも起こり得る |
| ★★★★☆ | 削除失敗が前面の確認Dialogから見えない | エラーは背面の編集Dialogだけに描画され、回復方法を判断できない |
| ★★★★☆ | 取込前の部分成功が予測しづらい | DB取込は有効/除外件数がなく、兵種取込も除外件数を完了後まで示さない |
| ★★★★☆ | フォーム状態の意味付けが不足 | 成功/失敗のライブ通知、必須入力との関連、確認Dialogの説明関連付けがない |
| ★★★★☆ | 国色保存の競合・失敗回復が不明瞭 | ローカルへ即反映後に全件PUTし、失敗時に画面を戻さない。方式変更は保存挙動へ影響する |
| ★★★☆☆ | DB/被弾表のフィルターが独自実装 | 共通`FilterPanel`と開閉、解除、結果通知、フォーカス復帰が重複する |
| ★★★☆☆ | 破壊的操作がnative confirmとDialogに分散 | 一括置換すると同期/非同期、対象保持、フォーカスの挙動が変わる |

## このPRで変更しないもの

- 兵種名変更をrenameとして扱うこと
- 編集途中の名前と削除対象の契約
- API payload、レスポンスキー、HTTP method
- 新しい数値範囲や必須規則
- 部分成功を全件失敗へ変えること
- 国カラーを差分保存へ変えること、失敗時rollback
- native confirmの一括Dialog化
- 認証方式、Cookie、DBスキーマ
- History/ログインの既に安定しているフォーム構造

未認証の兵種詳細から「編集」を隠す案は権限の認知を正す一方、既存のユーザー可視挙動を変える。保存APIの認可は既に安全であるため、このPRでは実施せず独立案として残す。

## 受入条件

- 既存のURL、method、payload、複合値をテストで固定できる
- DB/兵種取込で、実行前に有効件数と除外件数が分かる
- 成功は`status`、失敗は`alert`として通知され、同じ内容を二重通知しない
- 兵種名の必須エラーが入力欄と関連付けられる
- 兵種削除の説明と失敗が前面の確認Dialogから分かる
- Scoutの2種類のコピー対象と結果を支援技術で区別できる
- DB/被弾表のフィルター値、初期open、件数、並び順が変わらない
- 320 / 390 / 768 / 1024 / 1440pxで横スクロールや主要操作の重なりがない

## 確認方法

- `npm test`
- `npm run lint`
- `npm run typecheck`
- `npm run build`
- `git diff --check`
- 未認証/管理者の表示境界
- URL直アクセスとブラウザ戻る/進む
- 有効入力、不正入力、同名、部分skip、通信失敗、削除キャンセル/失敗
- Tab、Shift+Tab、Escape、Enter、Cmd/Ctrl+Enter
- Light/Dark、320 / 390 / 768 / 1024 / 1440px
- 保存成功/失敗はfetchまたはブラウザ通信を置換し、実データを更新しない

## リスク

- UIテスト環境はNode中心で、ブラウザ操作は実画面確認を併用する必要がある
- parserの`parsed`は同名をまとめた後の件数であり、重複行数そのものは返さない
- Unit削除対象の仕様が曖昧なため、見た目の改善中も対象名を変更しない
- 国色は全件PUTのため、保存方式へ触れると競合/rollbackの仕様決定が必要になる
- native confirmを非同期Dialogへ変えると、確認中の対象を固定する追加設計が必要になる
